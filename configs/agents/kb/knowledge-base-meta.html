Knowledge Base: Format and Conventions

Every agent reads and writes its own reusable knowledge directly. The kb skill describes the full process. This entry defines the storage format and maintenance rules.

Location and index

KB entries live at ~/.agents/kb/. In these dotfiles, that path uses ~/.dots/configs/agents/kb/. Version control tracks this format entry but ignores other local KB entries by default.

List the directory, including ignored HTML files, at session start. Read each entry's head metadata for the index. Read full entries only when they are relevant.

When to record

Write verified, reusable knowledge as soon as you learn it. Do not wait for task completion or a writer agent. A small fact qualifies when it prevents repeated work.

Keep project-only facts in the project's instructions or skills. Use the global KB for knowledge that applies across projects, including local environment behavior. Classify facts by where they apply, not by their source repository.

For example, a local jj wrapper can run Git hooks. Record its verified scope and command limits so future agents do not repeat those checks unnecessarily.

Filename

Use <slug>.html with lowercase words separated by single hyphens. Do not use numeric prefixes or leading or trailing hyphens. Keep the filename when you update an entry.

Metadata

  • title: a concise entry name.
  • description: a short summary for the index.
  • tags: comma-separated topics.
  • priority: high, normal, or low.
  • created: the original creation date in YYYY-MM-DD format.
  • updated: the latest content-change date in YYYY-MM-DD format.

Use high priority for frequent reuse or costly mistakes. Use normal priority by default and low priority for rare cases. Change priority when evidence supports the change.

Entry structure

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title>[Entry title]</title>
  <meta name="description" content="[Short summary]">
  <meta name="tags" content="[tag1, tag2]">
  <meta name="priority" content="normal">
  <meta name="created" content="YYYY-MM-DD">
  <meta name="updated" content="YYYY-MM-DD">
</head>
<body>
  <h1>[Entry title]</h1>
  <p>[Verified fact and where it applies.]</p>
  <p>[Useful action and limits.]</p>
  <p>[Evidence source and verification date.]</p>
</body>
</html>

Include only useful sections. One fact can be a complete entry. Use lists for steps and pre and code elements for commands.

Topic boundaries

Keep each entry focused on one topic. Merge new knowledge into an existing entry only when both cover the same topic. If topics are related but distinct, use separate entries and link them through a Related section.

Direct updates

  1. Check existing titles and descriptions before creating an entry.
  2. Update an existing entry when it covers the same topic.
  3. Read the latest content before writing, especially when another agent can change it.
  4. Preserve the filename, creation date, and unrelated correct content.
  5. Set the updated date to the current date when you change content.
  6. Record the evidence, environment scope, and limits of the fact.
  7. For corrections, explain what changed and why.
  8. Check the saved HTML and refresh the session index.

Do not store secrets, credentials, unsupported guesses, duplicate notes, or temporary task status. If permissions block a write, report the destination and note. Do not claim that you saved it.

Age and incorrect advice

List entries at least 180 days old once per session for user review. Age alone does not prove that an entry is incorrect. Do not delete entries or change their dates merely because they are old.

Correct an entry directly when current evidence proves it wrong. If the replacement is uncertain, report that uncertainty. Do not silently leave known incorrect advice without a correction or warning.

Correction history
