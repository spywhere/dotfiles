Knowledge Base: Format and Conventions

This is the meta-entry for the knowledge base itself. It describes how entries are structured, named, prioritized, and maintained. The kb-writer sub-agent must consult this entry before writing or updating any KB file.

Location

All KB entries live at ~/.config/opencode/kb/.

This directory is part of the global opencode config, symlinked from ~/.dots/configs/opencode/ in the user's dotfiles repository. Changes here are tracked in git.

File Naming

Pattern: <slug>.html

  • Slug is lowercase, hyphen-separated, derived from the entry title
  • No numeric prefix — entries are not ordered by filename
  • No consecutive hyphens, no leading or trailing hyphens

Examples: knowledge-base-meta.html, gitlab-mr-diff.html, jira-ticket-lookup.html

Slug derivation: lowercase the title, replace spaces and punctuation with hyphens, collapse consecutive hyphens, strip leading/trailing hyphens.

Entry Structure

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title>[Concise title]</title>
  <meta name="description" content="[One-line summary — used in the index]">
  <meta name="tags" content="[tag1, tag2, tag3]">
  <meta name="priority" content="[high|normal|low]">
  <meta name="created" content="YYYY-MM-DD">
  <meta name="updated" content="YYYY-MM-DD">
</head>
<body>
  <h1>[Title]</h1>
  <p>[Context: why this matters, when to use it]</p>

  <h2>Steps</h2>
  <ol>
    <li>...</li>
  </ol>

  <h2>Examples</h2>
  <pre><code>[commands or code]</code></pre>

  <h2>Notes</h2>
  <ul>
    <li>[Caveats, gotchas, environment-specific details]</li>
  </ul>
</body>
</html>

Required Fields

  • <title> — used in the index; concise and descriptive
  • description — one sentence; what the agent reads when scanning the index
  • tags — comma-separated; used for topic-based lookup
  • priority — see Priority section below
  • created — ISO 8601 date of first creation; never change this
  • updated — ISO 8601 date of last modification; update on every write

Priority

Priority controls which entries the agent fetches first when multiple are relevant. Set it honestly — not everything is high priority.

  • high — frequently needed, critical workflows, or high cost if forgotten
  • normal — default; useful but not critical
  • low — edge cases, rarely needed, or context that is good to have but not actionable

Priority can be updated at any time by the kb-writer sub-agent if experience shows an entry is more or less valuable than originally assessed.

Optional Sections

Include only sections that are relevant. Not every entry needs Steps, Examples, and Notes. Other useful sections: Prerequisites, Troubleshooting, Related, Warning. Add or remove <h2> sections as appropriate.

Updating an Existing Entry

  1. Keep the original filename — do not rename entries
  2. Update updated to today's date; preserve created
  3. Preserve existing content unless it is incorrect; prefer appending or amending
  4. If correcting a mistake (reactive cleanup), add a brief inline note explaining what changed and why

Deduplication

Before creating a new entry, scan all existing titles and descriptions. If an existing entry covers the same topic, update it instead of creating a duplicate. If topics are related but distinct, create a new entry and add a Related section pointing to the existing one.

Staleness

At session start, the agent flags entries not updated in 180+ days for human review. Stale entries are never deleted automatically — the user decides. When the agent uses an entry and finds it incorrect, it updates the entry reactively and records what changed.

Content Guidelines

  • Write for yourself (the agent), not for a human audience
  • Be precise — include exact commands, paths, flags, options
  • Include context for why something works a certain way, not just what to do
  • Note environment-specific details (OS, tool versions, network context) where relevant
  • Keep entries focused — one topic per entry; broad topics can be split
